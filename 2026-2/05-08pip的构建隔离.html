pip 的构建隔离

久违地去在 docker 里搭建 ML 项目，结果遇上好多坑，值得记一下。

CUDA in docker

关于在 docker 中使用 CUDA，要保证：

  1. WSL 版本最新
    1. 不要相信 WSL 的自动更新，直接从官方 git 仓库的 release 下 https://github.com/microsoft/WSL/releases/
    2. 它安装可能失败说对某注册表没有修改权限，直接给丫的删了
    3. 安装后重启电脑
  2. 更新 WSL 后，docker 也重装
  3. 保持显卡驱动最新
  4. 安装 CUDA toolkit（？存疑，我记得我之前尝试的时候并未安装这玩意儿）
  5. 按照 https://docs.docker.com/desktop/features/gpu/ 去检查当前 GPU 在容器中是否可用

pip 的构建隔离

pip 安装许多包（尤其是 ML 相关的）时候，需要检查所安装的包的 pyproject 去进行构建操作，这个我们都知道，但我以前不知道的是，这个构建操作中，pip 会在临时目录启动一个轻量的，干净的虚拟 python 环境，然后在线从 PyPI 中（仍旧走镜像源如果配置）下载符合 pyproject 中限定的版本的 setuptools，wheel 依赖，并使用它们去在虚拟环境中进行构建。

这个构建隔离选项，可以通过--no-build-isolation去关闭，但一般不推荐关闭，因为系统的 Python 环境远远称不上干净，会带来别的奇怪问题。

为什么在今天突然提到这个构建隔离？因为安装 CosyVoice 的依赖时，它依赖了 openai-whisper 的旧版本，而安装它会直接失败，and here’s why：

  1. CosyVoice 依赖的是 openai-whisper==20231117，它下载这个版本的 whl 并试图编译
  2. openai-whisper 的 pyproject.toml 中写着（它似乎就没改过）require：setuptools>=61.2
  3. pip 默认升级友好，即认为高版本总是向前兼容，所以 pip 安装了最新的 setuptools，版本大概大于 82
  4. 然而该旧版本 openai-whisper 用了一个所谓的 pkg_resources 包，而这个包，在 setuptools 中的 82 版本及其之后被移除
  5. 于是旧版本的这个 openai-whisper build 的时候就直接报错了

解决方案是，直接从 requirements.txt 移除 openai-whisper 的版本约束……要不然就只能做花活儿——专门把 openai-whisper 挑出来使用--no-build-isolation去安装，或者直接 fork 下来修改版本号再安装了。

顺便，只有 setup.py 的项目会设置一个 setuptools>40.8.0 的约束，同样会打到当前最高版本……

pyproject.toml vs setup.py vs requirements.txt

正好碰到了就再深入一下——pyproject.toml，setup.py，requirements.txt。这仨的区别在于：

  • setup.py：用于构建包的 python 脚本，基本已经弃用，由 pyproject.toml 替代
  • pyproject.toml：描述用于构建包的元信息的配置文件，当前主流标准；它是配置文件，因此可以更换用来解释和执行它的后端
  • requirements.txt：用于 pin 运行时依赖，用于开发和生产环境，与包的构建无关

setuptools，poetry 都是 pyproject.toml 的后端。

requirements.txt 的功能其实相当单纯，使用 pyproject.toml 也可直接声明依赖并让 pip 去安装。
