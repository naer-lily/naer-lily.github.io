实现 OpenAI 客户端 1——API，SSE 和工具调用

从零开始去实现一个 LLM 客户端（支持流式，工具调用）是一个把知识串在一起的好主意，所以就去做一下。完全古法编程！

使用技术栈：

  1. pydantic 进行类型定义
  2. httpx 作为 HTTP 客户端

我会依据 deepseek API 文档去进行实现，它相较于 OpenAI API 大概是多了几个字段，但就这样啦。为了方便，我会完全使用 async。

异步对话补全接口定义

事情开始不 trivial 了……？骗你的——还是很 trivial，因为 Python 有生成器和异步生成器，读写 SSE 洒洒水，哪像我以前在 Spring MVC 里写的痛苦……

httpx，乃至之前的 requests，都是支持流式返回的，我们知道 SSE 是一行一行来的，全部都以data:开头，然后每一行数据都是一个 json——通过 delta 流式地拼装请求体。

一个奇怪的地方是 SSE 的每个 data 中间有一个空行（或者说，SSE 以两个换行符分割数据），但我们不需要考虑这个——空行直接无视它即可。

注意到 deepseek 的 API，失败时 Deepseek 是直接返回 json 而非回到 SSE 了，所以我们在异常处理部分就不用流式了。

然后我们来写一个实际的一个流式的“renderer”来玩（还算容易），其实后面我们终究要写类似的东西。这里一个很坑的地方是，reasoning_content 和 content 可能是空字符串，所以我们必须判断 is not None。然后为了合适地塞 reasoning 标签，我们得做一点状态机，我们知道刚开始思考的时候和刚开始输出的时候我们要做操作。

增加工具调用参数

光对话已经跑起来了，最后的就是增加工具调用的参数了，当然我们不实际调用，只是让它支持能够调用。然后我们再写一个 renderer，这章就算结了。

这里瞧了一下 deepseek 关于 思考模式和工具调用 的文档，它提到了两点：

  1. 思考模式下，温度，top_p，频率惩罚等参数都是无效的
  2. 没有工具调用时，思考内容传给 AI 会被忽略，而一旦有了工具调用，则这之后任何 assistant 的思考内容也必须传给 AI（好像某些 LLM 客户端没有考虑这个，因为它们删去了思考内容所以直接报错了）

让 OpenCode 对了一下其他家的 AI，发现其实……总是回传思考内容是合适的。所以，我们为 AIMessage 也增加之前缺失的 reasoning_content 和 tool_calls（它们本来就是必要的）。

有三点：

  1. ToolDef 和 ToolCall 的定义（考虑到实践性，这一层不加泛型了）
  2. ChatCompletionBody 增加 tools 和 tool_choice
  3. AIMessage 和 ChatCompletionMessage 增加 tool_calls（巧了，delta 拼接的逻辑这一层还做不来）……

写完了，然后发现改的地方太多，这里不贴了，我要玩一些真正的花活了！

但他它的更多——它要能获取最终的整个 AIMessage，和 usage 信息。

我们需要一个 reducer——(AIMessage, MessageChunk) -> None（想不到吧？因为我们原地操作）
