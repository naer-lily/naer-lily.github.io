LLM 学习笔记 3——LangChain 和 RAG 粗探

写的很流水，因为它忠实地反映了我的复习（和学习……因为变了太多）的顺序 XD。

关于 LangChain 当前的架构

自从 v1（25-10-20）版本后，LangChain 已经完全转向——可以说，LangChain 是一个完全围绕于 create_agent 这个特殊的 StateGraph（来自 LangGraph） 去组织的框架。

LangChain 已经不再期待我们直接去使用 ChatModel，ChatModel 现在在概念上成为了 agent 的“推理引擎”。

实际上，在当前的 LangChain 的架构下我们要是还去用 create_agent，那我们就做不了 2-step RAG 了——没有入口让我们去改写 prompt（其实有，有相应中间件提供动态 prompt 功能），得自己写新 Graph。

但 LangChain 为 create_agent 这个特殊的图，相对于普通的 StateGraph 提供一些额外的机制，主要是中间件

  • tool 装饰器以及对 tool 的动态维护
  • 中间件（这里花活儿可多了）

所以，现在 langchain 依赖 langgraph（以前不依赖），而 langgraph 依赖 langchain-core。

LangChain

LangChain——一个 LLM 框架，它应该是最流行的那一批。

LangChain，LangGraph，Chain 是链表，这个跑完将其结果用来跑下一个，如同 FP 的 compose，而 Graph 则是一整个图，中间还能带逻辑的（而且还不是树逻辑），这是说，LangGraph 确实有 LangChain 实现不了的东西。

Runnable

LangChain 第一眼看下来，会发现它首先可以当成 openai_client 去用——每种 Message 抽象成类，同步、异步都支持，全部返回和流式返回都支持——invoke，ainvoke，stream，astream。此外还有 batch 和 abatch——并行 invoke、ainvoke。

LangChain 是按继承那一套去抽象的，看着头疼。Runnable 是一个重要的抽象基类，上面的 invoke，stream，batch 都是来自于 Runnable 的…但倘若大家都按 Runnable 去要求自己的参数的话，事情其实反而会变简单起来。

一般来说，原子的 Runnable 是无状态的，但如 CompiledStateGraph 它也是 Runnable，但他是有状态的。

Agent

Agent 在本质上是一个 StateGraph，看名字就知道了，有状态的图；我该不该吐槽这 LangChain 的例子，上来就创建 LangGraph 里的东西？

实际上观察 langchain 的文档的 Philosophy 部分，在 25 年 10 月 langchain 搞了一个重大的升级，现在的 chain 和 agent 确实都切换到了 langggraph 了……

官方示例提了两个 agent——langchain.agents.create_agent()和deepagents.create_deep_agent()（一个另外的包），前者是一个普通的 Agent，只能用你提供的工具，而后者则自带一些常用工具，包括文件访问，todo 工具，且自己就能创建子 agent，deep agent 等于是一个控制台的 Agent 了。（这个 deepagents 是 26 年 3 月才增加的）

我注意到一个重要的事实——以前的 create_react_agent，ReAct 这个词就直接消失掉了。这也能看出一个脉络了——以前 ReAct 还是一种提示词工程的 pattern，现在则已经被各大 LLM 直接内化了，它们从准备训练集的时候就考虑了 ReAct。结果这个词就已经不需要再提了，成常识了。

agent 的模式其实非常简单——input[-reasoning-action-observation]-output。这里 reasoning-action-observation 是可以循环执行的，直到 AI 认为已经足够，就是过去的 ReAct。

Tool

LangChain，它的 agent…没有实现为 class 而是只是一个普通的 StateGraph……但他并非那么普通，它支持中间件去向其中做一些操作……好吧，agent 的 StateGraph 究竟是长什么样，我瞧了一下 create_agent 的 graph 的图片表示，发现它和 create_react_agent 的结构是一样的。

我们学的其实是这个具体的 StateGraph 呗？但它也是一个上下文工程的例子了。

（LangChain 的）Agent 的工具可以静态注入——启动时注入，也可以动态注入——通过中间件，中间件需要处理工具的注册（即塞到请求里）和工具的实际执行。我能够设想——中间件是每次请求的时候都要执行的，就像 HTTP 框架的中间件。

middleware 机制，是专属于 create_agent 创建的这个特殊的图的。

题外话：流式工具调用和并行工具调用

openai API 工具调用的具体流程：

  1. AI 请求工具调用——同步时，tool_cools 塞工具调用数据（数组形式），包括这次工具调用的 id（供返回工具调用时做结果的索引），要调用的函数名，参数（用纯文本传 json）；流式时，以 delta 增量传，同一个 index 代表同一个工具调用。
  2. agent 客户端执行工具调用，然后以 tool 的 role，包含着 tool_call_id 去把调用结果返给 AI，每个工具调用一个消息
  3. AI 再根据上面的工具调用的结果去做操作。

Chain (old version)

让我们瞧瞧旧版本的 Chain。

Chain——其实就是 Runnable 重写了按位或运算符，让 Runnable 可以互相组合，就像 Haskell 中的.但顺序相反，或者像 unix 管道操作符——f | g = lambda x: g(f(x))。我们可以设想，在 invoke 时，langchain 先用输入去执行 f 的 invoke，再把结果拿去执行 g 的 invoke；在 stream 时，事情则会变得更诡异一些——这个流式是且只能是半流式——提示词必须构造完才能传给向量数据库，向量数据库必须检索完和改完提示词才能把它传给 AI，但 AI 这之后就能够流式地把输出塞给用户了。

Chain 使得 Runnable 之间可以互相组合，Runnable 也可以和普通的函数组合（trivial），但这里存在一定局限——在 chain 中使用普通函数的话，stream 会失效，即 langchain 会等前面整个流处理完毕之后再去把完整结果传递给该函数，如果还想要保持流式处理，就用生成器函数。下面实现一个流式翻译，因为使用了生成器函数，所以事情会变得不那么 trivial——生成器接受的是一个迭代器去表示整个输入的流。

但它的实现我认为有一点诡异——我下意识会认为，invoke 是通过 stream 去实现的，背后会 reduce 成 invoke 的结果，这样明显更加优雅（虽然我们需要到处提供 reducer），结果 tmd invoke 和 stream 在 langchain 中就不是一回事。

然后，异步就必须全异步，同步就必须全同步…这倒是不错啦。当然，真要做这种抽象，就自己实现一个 Runnable 而非是用这样 trivial 的函数或者生成器，这样明显是 ad-hoc 的操作。

RAG（LangChain 中的）

那还是 LLM 的蛮荒时代，RAG 被以为是什么时髦的东西。LangChain 为 RAG 做了原生的支持，将任何用于 RAG 的原子去抽象为 Document。

但现在 RAG 在 langchain 中已经成为很次要的东西了……半天找不到 RAG 的教程在哪里就。以前人们期待 LLM 成为有据可循的问答机器人，现在人们期待 LLM 能完成一切人类能完成的事情。但 RAG 在企业内部开发中可能仍旧重要，所以去回顾一下。

以前的那种 RAG 我之前管它叫 naive RAG，langchain 管它叫 2-step RAG，即先检索再生成，当前聚焦于 agent 的 langchain 已经无法直接实现 2-step RAG 了（但也不是不行……可以使用中间件去勾进去提示词部分）。

RAG 的经典过程——转换、切分、嵌入向量化，入库、查询（称为召回，因为我们的最终目的是得到原始文档的片段，从查询文本“召回”相应文档），其实就是把文档分块，为每块做倒排索引罢了，只不过这里索引用的不是关键字，而是嵌入向量化得到的每块的所谓语义向量。为什么要分块？因为一整个文档太大，语义信息太杂，不分块的话查询结果会有很多噪音（而且把上下文也给你挤爆）。

这里就重新抓一下 LangChain 关于 RAG 的抽象，它们每个角色是什么：

  • Document：所谓“文档”，它是语义查询的原子。Document 没有“chunk”——文档切分前是 Document，切分后还是 Document
  • Document Loader：加载各种类型文件的数据来源为 Document。一个文件可能对应一个 Document 也可能对应多个，全看 Loader 怎么实现（因为反正后面有切分步骤，这里随意）
  • Splitter：Document 切分器，接受 Document 列表，返回 Document 列表
    • 一个一般用途的切分器是 RecursiveCharacterTextSplitter，它递归地将 Document 按换行符去拆分（或者合并）直到所有块到达合适大小
    • 此外还有定长的切分器 CharacterTextSplitter
    • 还有基于 Document 结构的一些切分器，这类通常适用于结构化文本，如 markdown，html，json，乃至代码
  • Embedding：嵌入模型的抽象，这里需要意识到——每种嵌入模型生成的嵌入向量是不同的，所以每次更换嵌入向量的时候，cherry studio 等 LLM 客户端要求重新索引整个知识库
  • Vector Store：向量数据库抽象，能更换向量数据库的实现，langchain 自己提供了内存向量数据库。Vector Store 必须依赖 Embedding——它提供的接口遮蔽了 Embedding 的细节，直接操作 Document，插入 Document，查询 Document，但 Vector Store 的任何操作和具体的 Embedding 都是密不可分的。
    • 向量数据库支持多种查询策略——相似性，最大边际相关性（MMR），MMR 让所查询的结果之间的相关性更小以提升多样性
    • 向量数据库支持直接使用文本或嵌入向量进行查询（怎么这时候抽象泄漏了……？）
    • 注意——向量数据库并非是 Runnable，估计是因为向量数据库本身功能复杂，不能用一个 Runnable 直接替代，但它提供了另一幅面孔——
  • Retriever：直接来自 Vector Store，将 Vector Store 的查询功能包装成 Runnable（参数显然需要从创建时给定），它接受文本，返回 Document 列表
  • Document Compressor：根据查询去对 Document 列表进行压缩和转换，一般应用于重排序。Compressor 不是 Runnable（其实也可以是）

重排序——对 Vector Store 查询出来的所有 Document（数量会很多，远大于 top_k，比如 50-100 条之类的），对它们进行重新排序再去选出 top_k，排序方法有：

  • 交叉编码器：（一般是）使用一个更精确，更慢的 Transformer 架构的模型，将这些 Document 进行向量化并分别和 query 拼接，计算每个 Document 和 query 互相之间的注意力（注意力高则表明相关），选出 top_k 再拼到提示词里。
  • LLM 排序：让 LLM 去评分和排序
  • ……

能发现——重排序并不 trivial，它和 embedding 走的不是同一个路子，embedding 模型底层也可以是 transformer 架构，但 embedding 时我们不关心什么注意力，我们要的只是最后的反映这个句子的语义信息的嵌入向量，而一般来说这样得来的精确度必然没有交叉编码器高，因此这引入了重排序的必要性。

我们用一个例子把全流程跑通——“刻意练习”这个 PDF，读取、切分，选一个轻量级的嵌入模型，将文档嵌入和插入内存向量数据库中，选一个重排序的 Compressor，把整个 chain 搭好——retrieve -> rerank 混合生成一个包含重排序逻辑的 retriever，再转换成一个 agument prompt 的 Runnable，把它和 LLM 连起来，bingo。
