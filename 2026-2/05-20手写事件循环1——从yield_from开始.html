  3. 为事件循环增加 FUTURE 原语
  4. 抽象出一个一般的 EVENT 原语（event loop 的 loop），重新实现 SLEEP 和 FUTURE
  5. 整蛊：异步生成器怎么说？
  6. 实战：使用上面的思想将事件循环“寄生”在 Qt 的事件循环中实现异步编程

我们一步一步来，先实现基于生成器的简单事件循环，这里与其说是事件循环，不如说是定时循环。这一步里，我们先实现 1 和 2。

回顾协程

我们调用函数时，控制权被暂时转给函数，函数执行完成后，控制权又被还给我，我继续执行。函数是一种非对称协程——调用者将控制权丢给被调用者，被调用者的控制权只能返回给调用者。

但生成器呢？其实它也是非对称协程，但稍微更对称一些——控制权可以从调用者-被调用者来回倒，被调用者还能 yield from 给其他生成器……但归根结底，这里的被调用者的链条终究要回到初始的调用者（就像有个栈，实际上也有个栈）。即使是事件循环，事件之间也需要一个公共的调用者——事件循环。

考虑某个协程 A，A yield from B，B yield from C，这每一次 yield from，控制权实际上都回到了调用 A 的那个人，而这恰好符合我们的需求——我们确实需要它正好回到最初的调用者处，因为我要在这里做花活儿呢，而这里的最初的调用者，它就是事件循环了。事件循环调度 A，然后从 C 处返回出来，但我们看到的实际上仍旧是这里的 A 的一个“实例”，只是栈顶当前是 C……no，栈顶不是 C，栈顶必然是我们的原语，如后面要实现的 SLEEP 和 FUTURE。

考虑下面的这个流程（要对 yield from 有一个恰当的心智模型才好理解）：

  1. event_loop.run(A()), 我们的事件循环 run 一个协程（生成器）A 的实例
  2. 事件循环执行 next(A)，它会执行生成器直到他 yield 一个值
  3. 生成器 A yield from 生成器 B，这时候的语义可以说 A 委托 B 去对事件循环进行响应
  4. 生成器 B 的逻辑开始执行，它 yield from 生成器 C，所以 B 又委托 C 去对事件循环进行相应
  5. 生成器 C yield from 我们的原语 sleep（为了保证一致性，我们的原语通过 def sleep(ms): yield SLEEP(ms) 的形式去暴露，这样生成器 C 这里也是 yield from；但实际上这里等价于直接 yield SLEEP(ms)
  6. 上面终于看到一个真正的 yield 了！因此 SLEEP(ms) 被返回给了事件循环，事件循环把我们协程的实例去注册相应事件，如定时器事件
  7. 定时器事件到达后，事件循环重新调度这个协程——通过 send 把事件的结果发给协程顺便调度它（因此使用send而非next）。

这里有趣的地方在于，任意的“业务代码”如 ABC，它们通过 yield from，控制权终究会直接回到事件循环，这实际上就很符合我们的需求——任意一个协程要等待什么东西的时候，我们正好需要控制权回到事件循环让我们去做其他调度。更酷的是，就连函数调用栈都能被维持下来，这让异步代码的 debug 变得和同步代码一样简单。

关于 Python 的生成器（协程）的yield，以及yield from的心智模型

yield应当认为是非原子的，它是一个两步的操作：向调用者返回一个值（或 None）；暂停期待调用者的唤起。在唤起之前，生成器中当前执行的代码始终是yield XXX，协程在yield内部暂停。

调用者唤起协程时，会向协程传递特定的值或者异常，然后控制权交给协程去继续执行；倘若是传递特定的值，则该值会作为yield语句的返回值返回过来；倘若是传递异常，则异常会直接从field语句位置抛出。

唤起协程有三种方式——协程的send和throw方法，以及next函数：

  • send：传递给协程一个值，执行直到遇到下一个yield或完成执行，倘若是前者，返回下一个yield传过来的值。
  • throw：接受异常或异常类型，让协程在yield内部抛出异常，期待生成器的捕获，并继续执行（同send），使用生成器函数定义上下文管理器时内置库会使用该操作。
  • next：等价于send(None)。
  • close：等价于抛出GeneratorExit异常，这个异常相当基础（甚至不是 Exception 的子类），一般来说不能被捕获到，同时它也不会在调用方产生异常。

此外，刚创建的生成器不能执行send（非 None 值），这是符合逻辑的——没有人去接受它。但能抛出异常……此时生成器无法捕获它，它会立刻被传播回调用者，很有趣的设计。创建协程后第一次执行next时会激活协程，这一步称为预激（prime），一些框架提供装饰器会在创建时自动预激协程，但yield from语法是会自动预激协程的……？

协程结束执行后，它 return 的值会作为所抛出的 StopIteration 异常的 value 字段，注意 return 的值是无法通过 next 获取到的，因此它也不会出现在 for 中。

但考虑到协程是可以喂给它值的，现在事情变得复杂了。yield from现在应当理解为，委派（delegate）工作给子生成器，这个委派和其他语言的委派概念一样——实际工作不是我干的，我只接受它的结果，操作我就是操作我委派的那家伙。同时，yield from的返回值即为子生成器 return 的值。

实际上，yield from，其行为就等于把子生成器的代码原样拷过来一份，并把最后的 return 返回出来。yield无法直接地实现yield from，后者允许用户喂进来的值以及产出的值直接跨越嵌套的子生成器。
