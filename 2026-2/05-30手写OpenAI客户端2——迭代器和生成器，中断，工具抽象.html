复习

关于迭代器

这里正好更深入地理解一下生成器。我之前学的时候是只学了基于 yield 的简单的用法，但这里明显需要我更加深入了，现在我是库作者了。

我们先说迭代器协议——对一个可迭代对象（Iterable），iter 函数返回它的迭代器（Iterator），迭代器实现__next__，抛出 StopIteration 表示无法再迭代。

（for 循环和）iter 函数会（按序 fallback）：

  1. 直接执行对象的__iter__方法并获取它的返回结果作为迭代器（Iterator）
  2. 使用对象的__getitem__方法去包装一个迭代器（从 0 开始索引直到该方法抛出 IndexError，此时会包装成 StopIteration）

迭代器（Iterator）只需一个方法——__next__，每次调用时获取下一个值，抛出 StopIteration 表示迭代器完结。

但这里，for 和 yield from 的机制非常有趣——for 接受一个 Iterable 而非 Iterator；因此许多 Iterator 会实现__iter__并返回自己。

所以，当我们实现一个迭代器时，我们通常不仅需要实现__next__，也需要实现__iter__，但这并非强制要求，除非该迭代器绝不会被用户直接创建。

然后，上述所有都有异步设计，完全平行，不表。

关于生成器

生成器的实例有两种创建方式——生成器函数，和生成器推导式，两者殊途同归。

生成器 Generator 是 Iterable 也是一个 Iterator，它额外实现协程的方法——send，close，throw。但生成器的一个重要特点在于——其 return 的值会被包在一个 StopIteration 里面 raise 给调用者，而这个 StopIteration 对生成器自己是无感的。

对生成器，其__next__等价于send(None)。

这里的重点是，生成器包含 close 和 throw 方法——

  1. throw 即向生成器中正在 yield 的地方抛出异常
  2. close 即优雅关闭生成器，我下意识以为 close 就是 throw(GeneratorExit())，但其实不止

关于 throw 的行为：

  1. 调用者对生成器执行 throw
  2. 倘若生成器已关闭，直接在调用者处抛出异常
  3. 倘若生成器未预激（这里非常有趣），在生成器开头抛出异常，这个异常在生成器内无法捕获，因此必然会顺便关闭掉生成器
  4. throw 会在生成器的当前 yield 的位置 throw 一个异常
  5. 如果这个异常被捕获，则生成器正常执行直到下一个 yield 或 return
  6. 如果这个异常被抛到了顶层，异常会直接暴露给调用者，所以调用者也需要 try 它一下以保险

特别注意——即使使用 throw，生成器仍旧可能 return，需要 except 一下 StopIteration，所以这里应当认为其实 throw 也是正常业务逻辑，是一种特殊的 send。

关于 close 的行为：

  1. 调用者对生成器执行 close
  2. 倘若生成器未预激，直接关闭生成器，什么逻辑都不需要做；倘若生成器已关闭，什么都不做
  3. close 会在生成器当前 yield 位置 throw GeneratorExit 异常
  4. close 期待 GeneratorExit 直接被抛到顶层，倘若如此，它静默退出
  5. 倘若 GeneratorExit 被生成器所捕获且到达下一个 yield，抛出 RuntimeError 表示 GeneratorExit 被生成器 ignore，倘若到达 return，则静默退出

从 close 的行为看来，编写生成器时，不应当捕获 GeneratorExit 异常。

处理连接泄漏

我本以为我在处理中断，其实我在处理的是连接泄漏问题……中断并非是这一层的指责。

复习生成器后我才突然意识到，为了支持中断，我必须要把之前的 raw_generator 当作生成器思考，而非当作迭代器思考。好吧，我说的是其实是当成协程思考，但 python 里协程指的是别的东西。

根据我们上面的学习，要实现中断其实非常非常容易，我有个 plan：

  1. 我在 OpenAIResponse 这一部分，通过上下文管理器去实现对其 raw_generator，即其背后的 SSE 的流式请求的关闭
  2. 获取 response 时不再去尝试直接耗尽它，而是直接关闭 raw_generator

我们只动 OpenAIResponse。raw_generator 我之前实际上只期待它有迭代器的行为所以我的类型标注写的是 AsyncIterator，但我现在对它的要求并非只有迭代了，我要能中断它，这让我不得不将它的类型实际标注为 AsyncGenerator。

然后关于中断，我写完才意识到我好像不太需要这样操作……我这里处理的中断，和来自用户，来自前端的中断并非是一回事情……用户侧的中断其实非常容易——直接在 for 里检查现在是否要中断，要中断的时候直接 break。

工具抽象

实际上实现了上面的那一步后，OpenAIAPI 它自己就算实现好了，后面则是它的使用者的事情。

让我们先做一做好玩的事情——工具抽象。我会学习 FastAPI 的那种套路，通过一个 Route 对象的参数去进行注册，而非是直接通过一个通用的 tool 装饰器去进行注册，以去避免造成一个可全局访问的 ToolRegistry 之类的东西导致可能过度的耦合（比如我们定义的 ChatModel 没有走构造参数注入而是直接获取了全局的东西，这就会在后面的开发上影响我们的心智导致问题）。

在这一步里，我们就不考虑依赖注入了——LangChain 之类的框架中，工具定义支持按参数名 config 和 runtime 去注入特定参数，参数注入这一层我们大可再做一层封装，比如用 thread_local，但这里做了就偏离主题了。

这里主要有两个问题：

  1. 文档问题——工具的名称，描述，然而更蛋疼的——每个参数的描述（我还不知道这个究竟能不能做，因为 Python 中的文档字符串的格式多了去了，不知道有没有统一标准）
