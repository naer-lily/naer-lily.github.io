多模态工作原理

当你向 Codex 发送图片时：

  1. Moon Bridge 从消息中剥离图片，替换为占位文本 [Image #1 attached]
  2. 注入 visual_brief 和 visual_qa 两个工具定义
  3. DeepSeek 决定是否需要看图 → 调用工具
  4. Moon Bridge 拦截工具调用 → 将图片 + 分析提示发给 Kimi K2.5
  5. Kimi 返回图片分析结果 → 作为 tool_result 注入 DeepSeek 对话
  6. DeepSeek 基于分析结果继续推理和回复

整个过程不需用户干预，一次请求完成。

故障排查

真实踩坑记录

以下是实际使用中遇到的坑，如果你碰到同样的问题可以快速定位。

0. Web Search 工具注入导致输出乱码或工具调用失败

症状： DeepSeek 输出的对话内容被替换成原始的 <响应 tool_calls> 格式，或出现 “Model tried to call unavailable tool ‘web_search’” 错误。

原因： Moon Bridge 在 web_search.support: "auto" 模式下会自动探测并注入 web_search 工具定义到请求中。DeepSeek 可能调用该工具，但下游客户端（Codex/OpenCode）的可用工具列表中不包含 web_search，导致工具调用以原始格式泄漏到输出中。

解决： 将配置中所有 web_search.support 改为 "disabled"：

1. 切换到 WSL 后 Codex 弹出登录页面——分两种情况

Codex Desktop 在 WSL 模式下仍然读取 Windows 用户目录的 .codex（C:\Users\<用户名>\.codex\）。但 WSL 里的 app-server 需要通过 /mnt/... 路径访问 Windows 文件。Codex 会自动翻译大部分路径（如 marketplaces），但 不会翻译 model_catalog_json。

2. 切换到 WSL 后网络环境变化

症状： 在 Windows Native 模式下一切正常，切换到 WSL 模式后 Codex 弹出登录页面（同坑 1）。

原因： WSL 是一个独立的网络命名空间。

  • Windows 侧 127.0.0.1 指向 Windows 本机
  • WSL 侧 127.0.0.1 指向 WSL 自己，不是 Windows

如果 config.toml 里写的是 127.0.0.1，WSL 里的 Codex 根本访问不到 Windows 上的 Moon Bridge。

3. Windows Native 模式下 PowerShell 中文乱码

症状： Codex Desktop 在 Windows Native 模式下使用 PowerShell 执行命令，处理中文文件或输出时出现乱码。

原因： Codex 默认使用 Windows 内置的 PowerShell 5，其 UTF-8 编码行为不一致。

解决：安装 PowerShell 7。 从 github.com/PowerShell/PowerShell 下载安装。Codex 会自动检测并使用 PowerShell 7 替代内置的 5 版本，7 版本没有中文乱码问题。

实际上推荐使用 PowerShell 7 + Windows Native——WSL 在网络、文件路径等方面仍有一些水土不服。
