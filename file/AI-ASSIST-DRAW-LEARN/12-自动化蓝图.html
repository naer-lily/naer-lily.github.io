12 · 自动化蓝图（把改画工作流变成服务）

阶段：未来规划（第 4 周以后才碰）。当前先跑通 02/03 本地闭环。 标注：✅ 本会话实测验证 / 🟡 官方文档确认 / ⚠️ 社区方案未验证。

1. 目标架构（你的原话翻译成系统）

Krita（本地，你画画）
   │  ① 你的画（PNG）
   ▼
本地脚本 / Krita 插件（你已有 kritarunner / Python 脚本能力）
   │  ② POST /upload/image + ③ POST /prompt（API 格式工作流 JSON）
   ▼
AutoDL 实例上的 ComfyUI（以 API 服务模式运行）
   │  ④ WebSocket 进度 → 执行 W1-A / W1-B / W5 通道
   ▼
   │  ⑤ 输出：贴线版 / 理想版 / 并排对比图（工作流内自动拼图）
   ▼
本地归档（07 闭环：diff-notes + 对照图）

自动化边界（方法论红线）：自动化到"输出并排对比图 + 归档文件"为止。自评与差异自读永远是你的环节——这是 08 文档里"典型化主体是你"的直接推论：机器可以替你跑重绘，不能替你判断"哪里是缺点、哪里是特征"。

2. ComfyUI 侧：它天生就是 API 服务（✅ 已验证）

  • ComfyUI 内置 HTTP + WebSocket API：
    • POST /upload/image —— 上传你的画（工作流里 Load Image 引用文件名）
    • POST /prompt —— 提交 API 格式的工作流 JSON（{节点id: {class_type, inputs}}；UI 里"导出 API 格式"可得）
    • WebSocket —— 执行进度/完成事件
    • GET /view / /history —— 取输出图
  • 官方文档章节（本会话 sitemap 实测确认路径）：
    • https://docs.comfy.org/development/comfyui-server/api-examples （本地服务端 API 示例）
    • https://docs.comfy.org/development/comfyui-server/comms_routes （HTTP/WS 路由）
    • https://docs.comfy.org/development/comfyui-server/comms_overview
    • https://docs.comfy.org/development/api-development/workflow-api-format （工作流 API 格式）
    • https://docs.comfy.org/development/comfyui-server/api-key-integration （API Key 集成）
  • 推荐封装：自己写一个 ~100 行的小服务（FastAPI）包在 ComfyUI 前面，做三件事：
    1. 认证（ComfyUI 本身无认证——直接暴露公网等于裸奔）
    2. 业务接口：POST /redraw {image, 通道} → 内部调 ComfyUI
    3. 结果装配：返回并排对比图 + 元数据（参数、种子、耗时）
  • 为什么自己封装而不是直连：AutoDL 的公网映射是"任何人拿到 URL 就能提交"（无鉴权）；封装层 = 你的 API 网关，还顺带把"业务语义"（贴线版/理想版）从"裸工作流"里解放出来。

3. AutoDL 侧：随用随起的真实情况

3.1 关机 = 免费（✅ 官方计费文档）

按量计费"关机结束计费"→ 生命周期策略：开机干活，干完自动关机。

3.2 脚本化关机：官方推荐模式（✅ 官方省钱绝招文档原文）

bash
python train.py; /usr/bin/shutdown        # 无论成败都关机
python train.py && /usr/bin/shutdown      # 成功才关机
# 或在 Python 里：os.system("/usr/bin/shutdown")

官方文档（https://api.autodl.com/docs/save_money/ ）场景三原话：适合"不确定代码执行多久、希望执行完立马关机"。

3.3 无卡模式（✅ 官方文档）

0.5 核 / 2GB / 无 GPU，￥0.1/小时；同一主账号同时只能有一个无卡模式实例；用于传文件/修环境。

3.4 远程"脚本化开机"：官方公开文档没有（⚠️ 重要边界）

  • AutoDL 公开文档索引中没有开放 API 章节（本会话实测 docs 索引）→ 官方不提供稳定的远程开机 API
  • 社区存在 autodl-cli / Python SDK（号称基于"应用实例 API"，可开关机）——⚠️ 未验证，且第三方方案随平台变动可能失效，不要把业务依赖在它上面
  • 替代路线：浏览器自动化（Playwright 登录控制台点开机）——脆弱，仅作个人玩具
  • 现实建议：你的使用模式是"画画时用"——开机后保持 GPU 模式（按秒计费，画画期间成本即实际时长），画完自动关机（3.2 的模式）。全自动远程开机是锦上添花，等官方 API 出现再说。

3.5 开机自动拉起 ComfyUI（🟡 社区实践）

社区做法：把"启动 ComfyUI"写进开机启动任务（systemd / 自启动脚本），开机后 1~3 分钟服务就绪。⚠️ AutoDL 具体配置方式以控制台/社区最新实践为准。

4. 备选托管（不想管服务器时）

平台模式标注
fal.aiComfyUI 工作流托管为 API，按次计费，无服务器🟡 官方文档此前确认有 ComfyUI 支持（本会话复验时网络异常，未再次确认）

优点：随用随起是平台义务、自带认证；缺点：国内访问与支付门槛、输入/输出要走公网。

5. 成本与延迟模型（按量计费下）

项量级
冷启动（关机→开机→ComfyUI 就绪）1~3 分钟（开机启动任务自动拉起则无需人工）
单张重绘（预热后）20~60 秒（4060 档；AutoDL 卡更快）
费用按开机时长计（如 24G 卡几元/小时档）；画画的会话期间开着，干完自动关机

6. MVP 路径（未来，按序推进）

  1. 第一步（本地先行）：ComfyUI 本地跑通 → 用官方 api-examples 文档手写一次"脚本提交工作流、取回输出"（在本地 127.0.0.1 上做，零成本，这就是 ComfyUI API 的"从 NAND 到 CPU"）
  2. 第二步（上云）：把同一套脚本指向 AutoDL 实例（先手动开机），验证"传图→重绘→取图"闭环；加开机自动拉起 ComfyUI
  3. 第三步（生命周期）：接入"自动关机"（3.2 模式）；评估是否值得上社区开机 CLI（⚠️ 不依赖）
  4. 第四步（可选）：封装 FastAPI 业务层（认证 + 通道选择 + 并排图），Krita 插件调用

7. 验证记录

✅ 实测：ComfyUI 官方本地 API 文档章节存在（sitemap 确认 5 个页面路径）；Comfy Deploy 可达；AutoDL 省钱绝招文档（无卡模式 0.1 元/h、shutdown 模式）；AutoDL docs 索引无开放 API 章节 🟡/⚠️：fal.ai 复验失败（网络异常，此前会话确认过 ComfyUI 支持）；autodl-cli/SDK 未验证（README 404）；AutoDL 开机自启动配置方式未验证
